# Linux Services Source Map

Hardware services running on the tablet come from this repository and a pinned version of upstream `debian-piano`. When modifying a service, check both the unit's `ExecStart` and the build source of the corresponding script; `/usr/lib/piano/` on the device is the installed output.

Finger input is handled directly by `nt36532e` with no userspace reader. The matrix core is separated from SPI, firmware, and input reporting, using integer arithmetic for frame validation, baseline tracking, row/column denoising, local peaks, contact area, and centroid calculation; the input layer maintains ten slots and palm latching. Palm contacts do not assert `BTN_TOUCH`, and when a stylus frame cancels fingers, the driver reports the palm tool type before releasing the slots. See [pen input notes](../../../linux/userspace/pen/README.md#userspace-stylus-input-for-reference-comparison) for palm-rejection limitations.

The core first uses 16 valid frames to identify the matrix type, then takes the upper median per cell across 32 frames to establish the baseline. Denoising subtracts each column median followed by each row median; if 3-way selection exceeds its work budget, kernel sort finishes the step. When the span between the raw delta maximum and minimum is under 50, the denoised maximum is guaranteed to stay below 100, so denoising is skipped while applying the same baseline drift; all other frames are denoised and checked against the touch threshold of 200 to decide whether to scan for peaks and regions. The 60×40 decoder state takes roughly 175 KiB, allocated once at probe time with no further allocations on normal frame or recovery paths.

Frames with bad checksums or truncation are simply dropped without updating contacts or the baseline; brief sample drops do not break drags. Firmware reload, suspend, and driver removal release active contacts, and the baseline is relearned after firmware reload or suspend. SPI transfer failures release current contacts while keeping the baseline; if firmware reload fails during panel resume, the IRQ remains disabled. The raw-frame FIFO is allocated only when capture is explicitly enabled, so normal finger input does not consume that 4 MiB queue.

`piano-device-config` installs `piano-touch.service` together with the [`pen-control.py`](../../../linux/bsp/common/usr/lib/piano/pen-control.py) script it invokes. The service only initializes vendor GATT characteristics via BlueZ—it does not read THP/hidraw, write to procfs, or create uinput devices. It keeps waiting while BLE is not yet connected; coordinates and pressure are fused in the kernel, and calibration files are also installed by the config package.

`piano-touch-view` retains raw-frame capture and reference comparison features and is not run by any system boot service.

Hardware drivers load via standard OF, platform, SPI, and RPMsg modaliases, with dependencies expressed through the Device Tree, kernel suppliers, and deferred probing. Display, keyboard, wireless, audio, and video have no ordered userspace loading services. Any fix identified through hot-patching must be written back to the kernel, Device Tree, or corresponding program source.

Keyboard backlight uses the kernel LED node `nanosic::kbd_backlight`, controlled through UPower and desktop power components. UEFI passes the Bluetooth address to the kernel via standard Device Tree properties, and touchscreen decoding is triggered by device bind events. ADSP and CDSP auto-boot via the kernel `remoteproc` driver; the Device Tree no longer disables ADSP auto-boot, nor does it rely on userspace waiting for display handoff.

The keyboard folio and touchpad share the Nanosic MCU. The driver declares `nanosic/MCU_Upgrade.bin` (loaded at boot) via `MODULE_FIRMWARE`, ensuring distro initramfs generators bundle the firmware whenever they include the driver. The system supplies the firmware and the driver loads the code into the MCU's RAM without relying on post-desktop reinitialization.

Debian sid uses the distro-provided UPower instead of rebuilding a legacy daemon. In the signed source, `up-enumerator-udev.c` already enumerates LED hotplug events, and `up-daemon.c` updates the composite keyboard object while preserving the original `/org/freedesktop/UPower/KbdBacklight` interface. Debian and Nyarch share the GSD 51.0 patch, which asynchronously refreshes brightness and range through this standard interface, cancels stale requests, preserves the zero-brightness state, and adds no extra hardware services. SteamOS also uses the distro-provided UPower.

The camera service creates V4L2 loopback nodes before the user session starts and sends a systemd readiness notification; capture starts only when an application requests video. Camera drivers auto-probe via hardware modaliases, and `CAMERA_START=0` disables the imaging service. Update the unit and helper together on upgrades.

On 2026-10-08, hardware running `g086a94c4529d` bound the mainline interface driver `qcom-camss`, rear sensor `s5kjn1 7-0010`, front sensor `ov32d40 5-0010`, and focus actuator `dw9768 7-000c`. The stock final DT matches the existing [camera overlay](../../../upstream/debian-piano-current/boot/dtbo-piano-camera.dts): rear uses CCI0 master1, GPIO115/116, and CSIPHY1; front uses QUP2 SE1 I²C, GPIO4/5, and CSIPHY4. The kernel's `drivers/media/platform/qcom/camss/` already includes SM8750, CSID980, and TFE Gen4 support, and both sensors live in `drivers/media/i2c/{s5kjn1,ov32d40}.c`. This is not a case of porting missing drivers from scratch; `video40/41` are loopback devices, so enumeration alone does not prove working image output. After booting this build via standard BOOT, 30-frame short captures on both streams each yielded 28 frames from hardware; both front and rear previews were inspected with no recurrence of CCM `Bad address`. The rear image was sharper after waiting 90 frames than in the initial preview. Sustained frame rates, concurrent capture, and GNOME application behavior remain unverified.

Camera hardware is currently managed exclusively by `piano-camerad`; it configures CSID→TFE PIX, scaling, and NV12 output, and provides exposure, white balance, and focus control. The [WirePlumber configuration](../../../linux/bsp/optional/camera/etc/wireplumber/wireplumber.conf.d/50-piano-camera.conf) therefore disables `monitor.libcamera` and direct CAMSS nodes so applications use the loopback devices. Keep this configuration together with the service; do not remove it independently without a working replacement. Gaps in upstream libcamera support, TFE statistics and per-frame parameter interfaces, front-camera timing, concurrency, timestamps, and tuning licenses are consolidated in [kernel interfaces and libcamera](../hardware/camera-controls.md#kernel-interfaces-and-libcamera). Debian, SteamOS, and Nyarch share the same kernel adaptation; switching distros or upgrading packages does not supply these missing hardware interfaces.

Camera 3A refers to auto-exposure, auto white balance, and autofocus; these essential algorithms are currently implemented in `piano-camerad` using kernel sensor/ISP controls. In natural-light logs from the front camera, the highlight-pixel ratio varied between 3%..8%; the old AE abruptly dropped exposure by ~19% upon crossing 4%, then raised gain due to insufficient average luminance. The stability patch switches to a continuous highlight response, per-camera statistics filtering, an ~5% luminance error deadband, and a 6% single-step change cap, while keeping the existing exposure/gain split, white balance, and focus behavior. Because the user confirmed the test scene was natural light without indoor lamps, no 50 Hz anti-flicker parameter was forced in.

The fixed ARM64 `camerad` has been deployed. In a 900-frame on-device front-camera capture, the 810 frames after the initial 3-second startup held full-frame YAVG at 76.54..77.76, with exposure and both gains steady at 2808/15872/6958; the daemon's own local luminance metric stayed at 93..95 (their sampling regions differ, so the two absolute luminance values are not directly comparable). Only statistics were retained during capture; no camera video was saved. This confirms control-loop stability in that scenario, though sudden lighting transitions and full mode switches have not been measured, and it does not represent full stock 3A tuning.

## Charge Logging

The logger reads only power-supply, IIO, hwmon, thermal, Type-C, CPU/GPU frequency, and backlight interfaces. Each JSON record includes a UTC timestamp, boot ID, boottime, sampling duration, and read errors; values retain native sysfs units: power-supply voltage and current in microvolts and microamperes, power-supply temperature in 0.1 °C, thermal and IIO temperatures in millidegrees Celsius, and raw ADC readings with their scale and offset preserved. `power_w` is computed from the readings; PMIC and charge-pump inputs are stored separately, their sum serves only as an input estimate, and positive battery power indicates net charging while negative indicates net discharging.

Sampling runs every 2 seconds when online and every 60 seconds when offline; netlink plug/unplug notifications wake the wait early, and unknown states retry every 2 seconds. The MCA firmware summary is read at most once per minute—refreshed early on plug/unplug events and skipped while authentication is in progress—without writing to debugfs or enabling the charge-pump ADC. A single sensor read failure does not discard other data. The service does not inhibit system sleep.

`/var/log/piano-charge-monitor/samples.jsonl` stores the active log, with each segment capped at 1 MiB; full segments are compressed into sequentially numbered `samples-*.jsonl.gz` files. The active file, rotated segments, and compression staging files combined stay within 20 MiB, pruning the oldest segments first when space runs low. A file lock prevents multiple instances from writing to the same directory, and restarts truncate only an incomplete trailing line. The service is hardened with read-only system and kernel interface protections, allowing writes only to the log directory. See [Getting Started](../../user/getting-started.md#charging-logs) for starting, stopping, and exporting logs.

## Two Rootfs Build Paths

The generic multi-distro path uses [`tools/assemble_rootfs.py`](../../../tools/assemble_rootfs.py) to install the distribution, desktop environment, and explicitly selected BSP/runtime packages; [`tools/package_bsp.py`](../../../tools/package_bsp.py) packages local configuration according to `linux/bsp/manifest.json`. The config package itself does not auto-enable services and contains no kernel modules or native binaries.

Debian base images install `piano-device-config` from the signed APT repository, while SteamOS and Nyarch install it from the same `sunuefi` pacman repository. Touchscreen and USB services are triggered by udev rules inside the package. Camera configuration and diagnostic utilities are still assembled by the runtime stage; release images verify that package-owned hardware files are not overwritten by later steps.

Desktop packages are installed automatically during the rootfs build, with source and binary digests recorded in the distro manifest and build logs merged into CI's `logs.zip`. Standalone builds use `./build.sh gsd --sysroot <Debian root>`, `./build.sh gdm --sysroot <Debian root>`, and `./build.sh pipewire --rootfs <distro root> --output <package dir under build>`; these commands require root, operate solely on local build directories, and do not access the tablet.

Debian rebuilds the matching version of the PipeWire package set from signed sid sources while preserving Debian's original package split and dependencies. WirePlumber can still link video nodes even when a camera exposes no enumerable controls, and the fixed V4L2 capture path is provided by `libspa-0.2-modules`. On older Debian installations upgraded via standard APT, `pipewire-v4l2-source` becomes a removable empty transitional package, and the legacy plugin and its loader config are removed together. Fresh images omit this transitional package and do not install test or development packages by default. Before upgrading from an earlier plugin-only replacement, download the currently installed package set with APT to keep a rollback copy; once Debian sid advances, official mirrors may no longer host the matching older daemon and libraries.

Nyarch and SteamOS still independently rebuild the GStreamer plugin and `pipewire-v4l2-source` against the target system's exact daemon and library versions without replacing audio components. The patches address format enumeration and preferred formats, runtime caps, buffer-pool lock ordering, copying borrowed MemPtr buffers, and V4L2 copied frames held during recording; see [camera interface](../hardware/camera-controls.md#frame-timestamps-and-errors) for module selection and buffer management. `patches/pipewire/<version>/series.json` records upstream sources and patch digests; sources enter the cache only after full preparation, and builder changes invalidate stale package caches. The 19 format tests run serially with an isolated GStreamer registry that does not scan system plugins; they do not replace on-tablet verification of camera, screen recording, and screen sharing.

GDM starts the session only after a real KMS device exposes a display output. Device Tree temporary framebuffers are identified by platform driver rather than checking only the `ID_PATH` prefix, and render-only GPUs do not count as display-ready. Patches live in `patches/gdm/<version>/`, and Debian and Nyarch builds install standard packages for their matching versions. The fix reuses GDM's existing udev events and timeouts without adding display services, fixed delays, or desktop restart scripts. Hardware runtime installation also strips the display manager's legacy dependency on `piano-display.service` while keeping other user customizations intact. Software desktop screenshots only prove compositor rendering succeeded; internal panel output must be confirmed using active DRM planes together with a camera photo of the screen.

On Debian KDE, SDDM waits via `udevadm wait` for the internal display controller's DRM device before auto-login, preventing KWin from exiting when `simpledrm` is handed off. It matches by udev platform device path rather than depending on `card` enumeration order; login starts immediately once the device is ready, and after ten seconds it still attempts normal startup.

Lock-screen reauthentication also uses GDM's existing PAM and D-Bus channels. When a client cancels, the authentication session is closed without sending `Reset` back to the canceling client, avoiding a cancel-and-recreate loop in GNOME Shell 51. When a request is superseded or a client disconnects, the authentication session is closed and the PAM worker subprocess is stopped before freeing the object, because the worker still holds a session reference and releasing the request alone does not terminate it. This patch is shared across the Debian and Nyarch GDM series and does not alter password verification, lock-screen settings, or file descriptor limits.
